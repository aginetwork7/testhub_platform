## 字段定义

**优先级**

- 高：影响主流程可用性或正确性，应当优先排期。
- 中：影响稳定性、效率或可维护性，不阻塞当前使用。
- 低：改善体验或减少长期维护成本，可择机进行。

**状态**

- 待实施：已分析清楚，等待排期。
- 进行中：已开始，文档内应记录当前进展。
- 已完成：已实施并通过验收，文档内应补充实际结果与完成日期。
- 已搁置：暂不推进，文档内应写明原因与重新评估的条件。

## 新增计划的规范

文件命名用「领域前缀 + 主题」，小写加下划线，例如 `ai_testing_next_optimizations.md`、`infra_nginx_config_directory_mount.md`。

每份计划开头都应包含这组字段，便于维护清单：

```
- 编号：P-0X
- 领域：
- 优先级：
- 状态：
- 立项：YYYY-MM-DD
- 影响范围：
- 预估工作量：
- 依赖：
```

正文建议包含以下部分，其中「背景与证据」和「验收标准」不可省略，因为它们决定了这份计划是否值得做、以及做完怎么判断成功：

1. 背景与证据：问题现象、复现方式、已经掌握的数据。
2. 目标与非目标：明确边界，避免实施时范围膨胀。
3. 实施步骤：可执行的顺序，必要时分阶段。
4. 风险与注意事项：已知的坑、需要提前确认的事项。
5. 验收标准：可量化、可复验。
6. 回滚方案：涉及部署或配置变更时必须有。

## 约定

所有改动都在开发环境完成、提交，再通过部署流程发布到正式环境。正式环境（`agi7` 前缀的容器，代码位于 `/home/agi7/testhub_platform`）不接受任何直接改动，因为它本身是一个 git 工作区，直接编辑会让下一次部署的 `git pull` 冲突失败。正式环境只做只读排查。

数据库里的业务数据与环境配置不属于代码，本就应该在对应环境里通过前端页面或脚本维护，不受上述约定限制，但改动前应先备份。
